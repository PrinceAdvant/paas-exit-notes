Replacing a Heroku Redis add-on without losing queued jobs

Redis on Heroku is often used as both a cache and a job queue. These need different treatment when you run it yourself.

Decide what is in it

Cache data can be lost. Job queues usually cannot. Look at keys with redis-cli --scan --pattern '*' | head and identify frameworks that use it, such as Sidekiq or Bull.

Persistence

For queues, enable append only mode:

redis-server --appendonly yes --appendfsync everysec

Mount /data as a volume. For a pure cache, disable persistence and set maxmemory with allkeys-lru.

Memory limit

Without maxmemory, Redis grows until the OOM killer picks something, possibly your database. Set the limit lower than the container's memory limit.

Switching safely

Drain queues first: stop enqueuing, let workers finish, switch the URL, start workers on the new instance. For caches, just switch and accept cold misses.

Security

Never publish port 6379. Use a password and an internal network only. See Redis on a self-hosted PaaS for the application deployment side.
