Buildpacks or a Dockerfile: choosing how your app becomes an image

When leaving a platform that built your app automatically, you must choose how images get built. Both routes are valid.

Buildpacks and Nixpacks

They detect the language, install dependencies and produce an image. You write nothing, and upgrades to the build logic arrive with the tool. The cost is less control and sometimes surprising defaults, such as the Node version.

A Dockerfile

You decide the base image, layers and final size. It is more work, but behavior is explicit and identical on every machine.

A pragmatic path

Start with automatic detection to get running fast. Once the app stabilizes, write a Dockerfile with a multi stage build, pinned base image and a non root user.

Things to pin either way

  • Language version (Node, Python, Ruby).
  • Base image tag, ideally with a digest.
  • Dependency lockfiles.

Cache

Order Dockerfile layers so dependency installation comes before copying source. Builds become much faster. A platform that supports both styles on your VPS is described in building apps on a self-hosted PaaS.
