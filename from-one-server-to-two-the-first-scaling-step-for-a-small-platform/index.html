From one server to two: the first scaling step for a small platform

One server carries a surprising amount of load. When it stops being enough, scale in the least risky order.

Step 1: bigger machine

Vertical scaling is the simplest. Resize the VPS, which usually means a short reboot. Do this before anything more complex.

Step 2: move the database

A database on its own server stops competing with apps for memory and disk. Use a private network between machines, and restrict the port to the app server's address.

Step 3: a second app server

Run the same containers on a second host behind a load balancer or DNS round robin. This requires apps to be stateless: sessions in Redis or signed cookies, uploads in object storage.

What to avoid

Do not add orchestration complexity before you need it. Kubernetes is a large step with a large operations cost. Many products never leave step two.

Measure first

Find the real bottleneck with htop, iostat and slow query logs. Scaling the wrong layer wastes money.

Keep it simple to rebuild

Whatever you build, keep a script that recreates a server from scratch. scaling a self-hosted PaaS beyond one server describes a tool for running many apps from one place.
